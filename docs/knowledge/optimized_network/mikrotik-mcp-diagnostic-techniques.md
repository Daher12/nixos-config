Learned 2026-09-09 while diagnosing F13:

- In plan mode the ZCode host denies `mcp run_command` outright ("Plan mode only allows read-only, non-destructive tools") — even for read-only prints that cmdAllow permits. In plan mode, use only dedicated read-only MCP tools (get_log, list_interfaces, get_system_status, …); save `/interface wifi … print` probes for execution phases.
- `list_interfaces includeCounters` returns `last-link-down-time`, `last-link-up-time`, and `link-downs` per port — the fastest forensic check for historical link blips without needing log history. A real carrier loss registers at both cable ends within ms; transitions seconds apart = separate PHY retrains (marginal link signature). NOTE (2026-09-12): the MCP REST list_interfaces output sometimes omits the `link-downs`/`last-link-*` fields entirely — the hEX log (topics interface,link,poe) is then the only reliable link-event history.
- **CAP/satellite radio scans run fine from the controller** (verified 2026-09-12): `/interface wifi scan cap-wifi1 duration=10` on hap-ax2 works through CAPsMAN and returns the satellite-position RF view; with 0 peers on that radio it has zero client impact. cmdAllow `/interface wifi*` covers scan/monitor on hap-ax2 only — satellites themselves stay print-free via MCP.
- On wifi/AP interfaces the same fields count **client-association transitions** (radio going to zero associated clients), NOT radio restarts — a gap in `last-link-down/up` with no log events just means "no clients for a while". Don't misread as an outage event.
- Log retention is asymmetric: the controller (hap-ax2) rotates its memory log within ~7–8 h at roaming-log volume; the satellites retain weeks of caps-topic history. Pull event history from satellites, current-window state from the controller. The controller's `caps` topic returns **0 entries even with a full buffer** — CAP session history lives only in the satellites' caps logs (verified 2026-09-13: those contain the complete session/disconnect history).
- hEX log: filter topics `interface,poe,link,error,warning,critical` (excluding `account`) yields only ~200 entries since install — fully paginable in one get_log call; `poe-out` only logs `current_too_low` when protection actively cuts a port, so brief power sags are invisible.
- Per-client association/roam history: get_log with `topics: ["wireless"]` (ROS 7.21.5 wifi logs client events under `wireless`, NOT `wifi` — `wifi` topic returns 0 entries) + `prefix: "<MAC-prefix>"` gives a clean per-device roam timeline in one call. Roam lines read `roamed <mac>@<iface> to <mac>@<iface>`.
- `list_wifi_interfaces` `running` flag is unreliable for CAPsMAN-remote radios on the controller (shows false while clients are associated) and even for local radios; verify real state with `run_command "/interface wifi monitor <name> once"` (state + registered-peers; passes cmdAllow as `/interface wifi*` print-family, works outside plan mode).
- Hostname↔MAC mapping: `list_dhcp_leases` on hap-ax2 includes `host-name` — fastest way to resolve "which MAC is <device>".
- **Clock skew after unclean reboot (bit both sessions 2026-09-09):** pre-NTP log timestamps on a freshly booted router can be minutes off. hap-ax2 stepped `22:26:55 => 22:48:46` (21m51s) at its 22:48 boot; hEX stepped only 19 s. Before building event timelines, grep the `system` log for `ntp change time` / `cloud change time` entries and treat all stamps BEFORE the step as skewed; cross-check boot time against device uptime. Uptime readings (health checks) are immune; log chronology is not.
- **Scanning an occupied radio drops its clients (bit 2026-09-13 audit):** a `duration=10` scan pauses the radio ~10 s and re-homed ALL 5 associated clients network-wide (IoT lamp, media board, DELL, iPhone, yoga — full re-association wave within ~3 min; wifi2 link-downs 0→1 timestamped the BSS emptying). Prior audits only scanned 0-peer radios. Check `monitor <iface> once` registered-peers first; scan occupied 2.4 radios only when a brief outage is acceptable. Gate on client ACTIVITY, not just peer count — check last-activity/throughput first: the waipu stick was actively streaming (last-activity 0 ms) when the 2026-09-13 15:08 scan severed it and it never re-attached (device-side reconnect stall). Silver lining: scan waves are the only event that reliably corrects dozing campers (forced rescans moved MT8167B to its correct BSS twice) and exercise the steering path (yoga landed on 5 GHz per probe-delay). Also: `scan ?` fails via MCP run_command (no TTY help) — use the proven literal form `/interface wifi scan <iface> duration=10`.
- **No MCP path to power-off:** the MCP surface has `reboot` only — no shutdown tool, and `reboot` is the wrong op before a cable swap (device stays running, so pulling the cable still cuts power under load). `run_command /system shutdown` is outside cmdAllow (hap-ax2 scope: `/user*`, `/interface wifi*`) → graceful power-down = operator SSH `/system shutdown`. There is no "unplug data only" on a PoE feed cable: pulling either end cuts the powered device's power.
- **Passwordless admin SSH configured 2026-09-10 on all 4 devices** (operator-directed): host key `~/.ssh/id_ed25519` (dk@yoga) imported for user `admin` on hap-ax2/hap-ax2-cap/hap-ac-cap/hex-poe; `~/.ssh/config` has aliases (e.g. `ssh hex-poe`). MCP creds live in `~/.mikromcp/.env` (ROUTER_<ID>_USER/PASS, mcp-svc on all 4) — stage via `set -a; . file` + `nix-shell -p sshpass` (no sshpass on the base system). RouterOS quirks seen: `/user ssh-keys import` consumes the .pub file (a following `/file remove` errors "no such item" — benign), and an error mid-command-line aborts the remaining commands in that SSH line; first key-auth test right after import can transiently fail — retry once.
- **RouterOS PoE devices boot on power APPLICATION, not availability:** after a graceful `/system shutdown` with the cable still connected, the box stays OFF when the rest of the network returns — it must be power-cycled (brief unplug/replug) to come back. Power-cutting a device that is already shut down is safe (no unclean-poweroff risk). Corollary: shutting satellite PoE loads down before the primary's post-swap boot reduces hEX rail load during boot inrush (Sep 4 brownout boot-loop mitigation).
- **`manage_dhcp_lease` contract (C024 drafting, 2026-09-13):** has `dryRun` but NO `confirmationToken` parameter — unlike e.g. `manage_dhcp_server` — so the host `ask` prompt is the only approval gate for it. `make-static` converts in place (address, client-id preserved) and the lease's `dynamic` flag flips to false immediately while staying bound → immediate read-back validation works right away. Selector is MAC, case-insensitive exact match; pickier than needed for hosts with client-ids (e.g. nix-media's DUID-style `ff:56:50:...`), which make-static preserves — but an OS reinstall regenerating a DUID silently misses the static lease (falls back to dynamic).
- **`make-static` is BROKEN at execution in MikroMCP 1.10 AND 1.11.0; dryRun = false negative (source-verified 2026-10-04):** the dryRun branch returns a client-side simulated diff BEFORE any REST call, but the real path does `routerClient.update("ip/dhcp-server/lease", id, {dynamic:"false"})` → `PATCH /rest/ip/dhcp-server/lease/{id}` with the read-only `dynamic` in the body → RouterOS HTTP 400 `unknown parameter dynamic`. A dryRun PASS therefore proves nothing about write fitness — for any MikroMCP tool, check `dist/main.js` execution path, not dryRun, when a write previously failed. `action=remove` is NOT affected (plain DELETE, no body). Workaround = privileged single-command script (`/ip dhcp-server lease make-static [find mac-address=<MAC>]`) via manage_script/run_script (C024 v2, sealed 2026-10-04).
- **RouterOS 7.23.5 lease-menu console referencing (probe-verified 2026-10-04):** bare MAC/address tokens are rejected as bare tokens (`print <token>` → "bad parameter"), and this menu's `print` takes NO `numbers=` at all — so bare-token resolution for make-static/remove can't be tested read-only via print. Use the find-expression idiom `[find mac-address=<MAC>]` (documented, deterministic); verify single-match read-only with `ssh <host> ':put [/ip dhcp-server lease find mac-address=<MAC>]'` → internal ID(s). `run_script` is fire-and-forget (`POST /rest/system/script/run`) — validate by read-back + `get_log` for script errors.
- **Health-probe latency baseline (all-4 check 2026-10-05):** hap-ac-cap answers `check_router_health` in ~7 s (CPU ~20%, ~18 MB of 128 MB free) while the other three answer in <1 s — that is its normal profile on 128 MB hardware, NOT an MCP/network failure. Judge stack health by whether all probes fail/hang together, not by one slow device. (All four were ROS 7.23.5 long-term, healthy, at that check.)
- **Controller memory ring = exactly 1000 entries (empirical 2026-10-05):** a busy roam-churn evening had rotated everything older than ~10 h out by 22:46 (guest-morning evidence before 12:40:48 unrecoverable). When an incident may need forensics, pull logs EARLY — the ring, not the 24 h window, is the real retention. get_log mechanics: when >500 entries match sinceMinutes=1440, output paginates OLDEST-first ("1000 matching entries, showing 500 (offset 0)") — a second call with offset=500 is required to reach the recent half. **Retention mechanics (log-config verified 2026-10-05):** every logging rule targets `memory` only — the `disk` action is an untargeted default stub and `remote` points at 0.0.0.0 (unconfigured) — and a non-default `topics=wireless → memory` rule (added during the AP investigation) floods the ring at ~3 debug lines per association event, so one churn evening erases ~10 h. When infra logs rotated out, the CLIENT keeps its own history: Windows `netsh wlan show wlanreport` / Event Viewer WLAN-AutoConfig/Operational covers the router's lost window (used as the 10-05 morning-forensics recovery path — see [[wifi-incident-2026-10-05]]).
- **`bulk_read` contract quirks (probed 2026-10-28):** it requires EXACTLY one of `routerIds` or `tags` — calling with neither (hoping for default/all) fails `BULK_TARGET_REQUIRED`; and it refuses fleet-level tools as `toolName` (`check_router_health` → `BULK_SELF_REFERENCE`) — fan out those per-device directly instead. `get_upgrade_status` via bulk works fine but returns `latestVersion: null` fleet-wide: the on-device update-check cache is never populated until a check is triggered (execution-mode op), so "is 7.23.5 current?" must be answered from web sources unless you run `manage_upgrade action=check`.
- **`list_bridges` is the RSTP forensic view:** per-port debug-info carries the full port state machine; verified baseline (2026-10-05): main `bridge` ROOT = satellite hAP ax2 CAP (04:F4:1C:72:AE:51) by MAC tiebreak (all priorities 0x8000), primary's root port = ether1 via hEX — that asymmetry is normal, not a fault. Bridge-port "inactive" status on wifi ports with zero clients = idle-BSS semantics (see [[f13-uplink-rootcause-status]]), not breakage; guest-dhcp enabled + ports attached proves the guest L2/L3 path intact even with no guest clients.
