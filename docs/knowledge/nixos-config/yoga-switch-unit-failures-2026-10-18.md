Three generations of switch fallout on yoga, 2026-10-18/19. Generations: 186 (23:04, first batch switch) → 187 (00:09, my broken instance-level fix) → 188 = dp55c0ri (00:46, template-level fix live).

**1. kitty `lucid-glass.conf` persistence — RESOLVED, one-time collision.** Impermanence mount-file refuses an existing plain file; /persist copy was byte-identical; **I removed it with plain `rm` as dk from the ZCode shell (works — only systemctl needs sudo)**. Gen 188 started the mount cleanly (`home-dk-.config-kitty-lucid\x2dglass.conf.mount` new unit, green).

**2. zram instance-unit shadowing (gen 187) — fixed.** Instance-level `systemd.services."systemd-zram-setup@zram0"` emits a standalone unit that SHADOWS the upstream template (ExecStart-less → systemd "Refusing." → dev-zram0.swap "bad unit file setting"). Rule: extend upstream template units at TEMPLATE level (`"systemd-zram-setup@"`), never instance; `%i` carries the instance; template-level also inherits nixpkgs's util-linux PATH and its own `restartIfChanged=false` pin (zram-generator.nix, cites systemd/zram-generator#226). Gen 188 verified clean: only template + drop-in, ExecStartPre present. Gotcha that cost a wrong turn: `grep -r` on /run/current-system/etc/systemd/system misses the symlinked unit tree — use `grep -R`.

**3. THE REAL REMAINING BUG (found 00:46, gen 188): on zen 7.2.9, `zramctl --reset` REMOVES the device.** Kernel journal, one second after my ExecStartPre "reset" ran: `zram0: detected capacity change from 31059968 to 0` then `zram: Removed device: zram0` → /sys/block/zram0 gone → generator ExecStart ENOENT on comp_algorithm. `zram-generator --setup-device` cannot hot-add; only the generator-as-generator at boot (or manual `cat /sys/class/zram-control/hot_add`, READ-triggered, returns new device id) creates devices. Live state after 00:46: module loaded, ZERO zram devices, hot_add available, disk swapfile carrying the system. **Both `zramctl --reset` recipes are wrong for this kernel: my staged ExecStartPre heal in modules/features/zram.nix AND the s2h hook recovery in yoga-s2h.nix (commit 44b405f — see [[yoga-hibernate-status]]).**

**Correct fix EXECUTED+STAGED 2026-10-19 ~00:55:** heal = ensure-fresh in the template ExecStartPre (`zram-reset-if-stale %i`, modules/features/zram.nix): in-use or disksize 0 → exit 0; initialized-no-swap → reset (removes on 7.2.9); device missing → `cat /sys/class/zram-control/hot_add` + verify `zram$id == $dev` (mismatch → hot_remove + exit 1). s2h hook resume branch reduced to restart-the-unit (ExecStartPre owns the dance; missing device no longer a dead-end warning). REPO_OVERVIEW gotcha rewritten (trigger + fix + 7.2.9 reset-removes + shadow trap; recovery = `new=$(sudo cat /sys/class/zram-control/hot_add)` then start both units). QC green: services attrNames == `["systemd-zram-setup@"]` (no shadow), drv escaping verified, bash -n, dry-builds yoga+latitude.

**Key exoneration:** the 00:46 switch itself did NOT touch zram (journal shows no stop/restart of the swap; pins worked — s-t-c skipped both units). The 00:46:20 failing run was the 2-min retrier hitting the freshly daemon-reloaded valid unit. **Retrier identified from journal:** systemd re-queuing dev-zram0.swap activation via the device unit — `dev-zram0.device: Job dev-zram0.device/start timed out` (90s job timeout) at :51 every 2 min; earlier :21 stamps were immediate EBUSY fails while the device existed. Benign once healthy; doubles as auto-heal trigger (a correct heal + one switch → retrier brings swap up within ~2 min, no manual start).

**User's "is rebuild+boot instead of live switch a permanent solution?" — answered NO:** boot starts from a fresh hot-added device (race impossible), so it dodges the failure, but every live switch after a zram-generator store-path bump re-triggers the teardown (s-t-c restarts changed swap units unconditionally; raw units can't carry X-RestartIfChanged), and boot-only wouldn't cover the s2h resume path at all. Permanent fix is the config heal above. Also: gen 187 was reboot-DANGEROUS (shadow unit refused at boot too) — "just reboot" is only safe on a verified-clean generation.
